# ROADMAP — мобильный ИИ-меш-кластер: дробление 16B-модели на ~5 устройств

Документ для планирования **до** реализации. Отвечает на три вопроса из обсуждения:
(1) как реально расшардить 16B на ~5 телефонов, (2) транспорт (в т.ч. упущенный момент),
(3) USB-OTG узел. Держим оба формата: **LiteRT** и **GGUF** — но с разными ролями.

---

## 0. Гейтовое решение: РАНТАЙМ определяет, возможен ли шардинг вообще

Это первое, что нужно зафиксировать — от него зависит весь остальной план.

| Движок / формат | Истинный шард по слоям? | Как | Роль в проекте |
|---|---|---|---|
| **LiteRT LLM** (`.task`, MediaPipe tasks-genai) | ❌ **нет** | гоняет модель целиком, не отдаёт hidden-state между слоями | «вся модель на 1 сильном устройстве» / маленькие модели / роутинг запросов |
| **GGUF + llama.cpp** | ✅ **да, уже готово** | `ggml-rpc` / `rpc-server` + `--rpc host:port` распределяет слои по узлам; layer-split встроен | **основной путь к 16B/5 устройств** |
| **ONNX Runtime Mobile** | ✅ да, но нужен оффлайн-экспорт | суб-модели, разрезанные по границам слоёв (`SHARDING.md`) | опция/альтернатива, если нужен ORT/NPU-делегаты |

**Вывод (решение зафиксировано 2026-07-16).** 16B нельзя расшардить через LiteRT — это
архитектурное ограничение, не баг. Работаем **двумя параллельными треками**:

- **Track A (основной, ближний срок): LiteRT + chat UI + «routing mesh».** Каждое устройство
  держит **целую** (хорошо оптимизированную под мобильные) LiteRT-модель; меш = discovery +
  маршрутизация запросов + failover.
  ⚠️ **Важно называть точно:** это даёт **пропускную способность (параллельные запросы) и
  отказоустойчивость**, но **НЕ ускоряет один токен-поток** и **НЕ запускает модель больше
  устройства** — LiteRT не режется по слоям. «Ускорение» здесь = больше запросов/сек на
  кластер, а не меньше задержки на один ответ.
- **Track B (параллельно): GGUF/llama.cpp true-shard** — единственный путь к «16B на 5
  устройств» (модель больше одного устройства). ONNX — запасной вариант.

exo-core в обоих треках — **дирижёр** (discovery/placement/security/health); тензоры двигает
LiteRT (целиком, Track A) или llama.cpp RPC (по слоям, Track B).

**Роль exo-core / HELIX меняется соответственно:** ядро **не считает тензоры**. Оно
**дирижёр** — discovery, идентичность/безопасность, аттестация, placement (какому
устройству какой band), health/аренда, оркестрация. Собственно тензорную математику и
передачу активаций для сессии выполняет **llama.cpp RPC (GGUF)** или **ShardRunner (ONNX)**.
Это ровно тот же паттерн, что уже есть в exo-core (инференс — в хосте через `BridgeBackend`,
транспорт — в `bitchat-core`), только добавляется контракт `GgufRpcBackend`.

> Почему не «просто взять llama.cpp RPC и всё»: у него **нет безопасности, нет
> устойчивости к уходу узлов, сырые тензоры по сети (полоса)** и он рассчитан на
> стабильный LAN. Это и есть зона ответственности exo-core/HELIX сверху — discovery,
> шифрование, аттестация, аренда/миграция, выбор кольца. llama.cpp двигает тензоры,
> HELIX делает из набора телефонов **кластер**.

## 1. Математика: влезет ли 16B в 5 телефонов

Квантизация **обязательна**:

| Точность | Вес 16B | ÷5 устройств (полоса весов) |
|---|---|---|
| FP16 | ~32 ГБ | 6.4 ГБ — нереально |
| INT8 | ~16 ГБ | 3.2 ГБ — тяжело |
| **Q4 (Q4_K_M)** | **~8.5–9 ГБ** | **~1.7–1.8 ГБ/устр — реально** |

Но полоса весов — не единственный расход RAM на устройстве:

- **KV-кэш** (локальный, только для своих слоёв). Для GQA-моделей относительно небольшой;
  при контексте 2–4K держать в **Q8-KV**, бюджетировать заранее (сотни МБ на весь ринг,
  делится по устройствам).
- **Буферы активаций** + рантайм-оверхед llama.cpp.
- Практический бюджет на приложение: держать **band весов + KV + рантайм ≲ 2.5–3 ГБ** на
  устройство. Для телефонов с 8 ГБ RAM — впритык, с 12 ГБ+ — комфортно.

**Prefill vs decode — разные профили по полосе (важно для транспорта):**

- **decode**: hidden-state = `d_model` float/токен/хоп. Для 16B `d_model≈5120–6144`,
  FP16 ≈ **10–12 КБ/токен/хоп**. При 5 устройствах ≈ 5 хопов, 10 ток/с → ~0.5–0.6 МБ/с —
  тривиально даже для BLE-всплесков, легко для Wi-Fi.
- **prefill**: hidden-state = `d_model × seq_len` разом. Промпт 512 токенов → **~5 МБ/хоп**,
  ×4 хопа ≈ **20 МБ** только на один прогон префилла. **Вот где полоса решает** и где нужны
  backbone-линк (USB/Wi-Fi Aware) и компрессия активаций.

## 2. Транспорт (упущенный момент): discovery и дата-плоскость — это РАЗНЫЕ радио

Главная мысль, которую легко упустить: **«найти узлы» и «двигать тензоры» — разные задачи с
разными требованиями, и их не надо гнать по одному каналу.**

| Слой | Радио/линк | Полоса | Свойства | Что несёт |
|---|---|---|---|---|
| Discovery/control | **BLE (bitchat)** | низкая (~0.1–1 Мбит/с практ.) | always-on, маломощно, multi-hop mesh, дальность | присутствие, `ANNOUNCE`, `LEASE`, heartbeat, ключи |
| Data (телефон↔телефон) | **Wi-Fi Aware (NAN)** | высокая | P2P без точки доступа, API 26+ | активации, префилл, токены |
| Data (IP-линк) | **Wi-Fi Direct / общий LAN** | высокая | нужен group owner / AP | то же, если Aware недоступен |
| Data (backbone) | **USB-OTG** | очень высокая (480 Мбит–5 Гбит) | проводной, стабильный, без разряда RF | самый тяжёлый хоп / не-телефонный узел |

**Ключ к архитектуре:** всё, что можно, **сводить к IP** (Wi-Fi Aware/Direct/LAN/USB-tether
дают IP-интерфейс) — тогда один `WifiMeshNetwork`/`IMeshNetwork` несёт кадры **по любому из
них без изменений**. BLE остаётся отдельным низкоскоростным каналом для presence/control.
Это подтверждает уже принятое в exo-core решение «протокол независим от транспорта» — его
надо просто довести:

```
        ┌───────────── control plane (низкая полоса) ─────────────┐
        │   BLE / bitchat: presence, ANNOUNCE, LEASE, heartbeat    │
        └──────────────────────────────────────────────────────────┘
        ┌───────────── data plane (высокая полоса, IP) ───────────┐
        │  Wi-Fi Aware  ┃  Wi-Fi Direct/LAN  ┃  USB-OTG (usb0)     │
        │        → один IMeshNetwork поверх IP несёт активации      │
        └──────────────────────────────────────────────────────────┘
```

Это и есть «то, что упустили»: не «BLE **или** Wi-Fi», а **BLE для контроля + IP-линки
(Wi-Fi Aware/USB) для данных**, с единой идентичностью узла поверх обоих радио.

## 3. USB-OTG узел — конкретика

USB даёт то, чего нет у радио: **полосу 480 Мбит–5 Гбит, стабильность, низкую задержку и
питание** (узел не разряжается). Идеальный **backbone для самого тяжёлого хопа** или для
подключения **не-телефонного «большого» узла**.

Два способа реализации на Android:

- **Вариант A — USB-tethering / NCM/RNDIS → `usb0` (IP).** Проще всего: USB поднимает сетевой
  интерфейс с IP, и **существующий IP-mesh транспорт работает поверх USB без единой строки
  нового кода**, на скорости USB. Лучший вариант для связки **телефон ↔ Linux-SBC**
  (Jetson/Orange Pi/RPi) — SBC как хост или как узел.
- **Вариант B — AOA / raw bulk endpoints (`UsbManager`, Android Open Accessory).** Больше
  работы, но даёт максимальную пропускную и позволяет подключать **не-Android узлы** (MCU,
  SBC, NPU-стик). Нужен для «телефон↔телефон по USB» (там есть нюанс «кто host» — один
  телефон в роли USB-host через OTG, другой как accessory) и для гетерогенных узлов.

**Топологическая идея (сильная):** поставить **проводной «большой» узел** (Jetson Nano/Orin
или Orange Pi с NPU, много RAM) на USB-backbone и отдать ему **самый тяжёлый средний band**,
а телефоны держат лёгкие band'ы по Wi-Fi Aware. `partition.py` (memory-weighted split) уже
это поддержит — узлу с большей заявленной (и **аттестованной**, см. Phase 5) ёмкостью
достанется больше слоёв. USB как backbone снимает боттлнек префилла на тяжёлом хопе.

## 4. Дорожная карта по фазам (2 трека)

**Решение зафиксировано:** **Track A (LiteRT + chat UI, основной, ближний срок)** и
**Track B (GGUF/llama.cpp true-shard, параллельно, для моделей больше устройства)** идут
одновременно; **USB отложен** на Phase 4. Фазы устойчивости/оркестратора (5–6) — общие.
Первым делом в любом случае — фиксы блокеров из `AUDIT2`.

### A0 / B0 — фундамент (сейчас, общий)
- **Починить блокеры из `AUDIT2`** до любой распределёнки: регрессия `from_node=""`
  (координатор-последний-стейдж), вернуть шифрование (AEAD), лимит кадра, секвенирование.

### Track A — LiteRT «routing mesh» + chat UI (основной)
Каждое устройство держит **целую** LiteRT-модель; меш даёт **пропускную способность
(параллельные запросы), отказоустойчивость и роутинг** — НЕ ускорение одного токен-потока и
НЕ модель больше устройства (см. §0).

- **A1 — 1 узел:** LiteRT `.task`, chat UI, `world_size=1`, `BridgeBackend`. Turnkey-генерация.
- **A2 — routing mesh:** discovery + маршрутизация запросов на N устройств (каждое с полной
  моделью); `get_cluster_nodes` / `infer_on_cluster` из `INTEGRATION.md`. **Результат:**
  кластер телефонов обслуживает больше параллельных чатов + failover.
- **A3 — оркестратор-lite:** роутинг по нагрузке/батарее/температуре (часть HELIX ⑤).

### Track B — GGUF/llama.cpp true layer-shard (параллельно, для 16B/5)
Единственный путь запустить модель **больше** одного устройства.

- **B1 — сборка:** llama.cpp под Android (NDK), `rpc-server` на 1 устройстве.
- **B2 — 2 устройства, истинный шард:** llama.cpp RPC поверх Wi-Fi/IP, hidden-state по сети;
  exo-core делает discovery+placement (`partition.py`/`sharder.py` готовы), контракт
  `GgufRpcBackend` (Kotlin ↔ llama.cpp rpc). **Критическая веха** — доказывает hidden-state
  passing на железе.
- **B3 — 5 устройств, 16B Q4:** memory-weighted band'ы, KV per-band (Q8), prefill+decode,
  компрессия активаций (FP16→INT8) на боттлнек-хопах (особенно префилл).

### Phase 4 (ОТЛОЖЕНО) — USB-OTG backbone + SBC/NPU «большой» узел
Вернуться после Track B: USB-tether→IP (Вариант A) или AOA (Вариант B); тяжёлый band на
проводной/сильный узел. Гетерогенная топология phone+SBC.

### Phase 5 (общая) — устойчивость и безопасность (HELIX ②④)
- **Аренда слоёв + heartbeat + миграция шарда** при уходе/разряде узла (resume с чекпойнта
  hidden-state), failover координатора. Снимает SPOF и churn.
- **Групповой ратчет (MLS-класса) + AEAD-шифрование** вместо общего HMAC; идентичность узла.
- **Аттестация ёмкости** вместо самодекларации (закрывает «ложь о памяти»).
- **Результат:** узел может уйти/сесть посреди генерации, а кластер продолжит; данные
  зашифрованы; ёмкость нельзя подделать.

### Phase 6 — интеллектуальный оркестратор (HELIX ⑤)
- Пересчёт placement каждые N секунд по **нагрузке / температуре / батарее / RTT / NPU**;
  QoS-классы кадров (TOKEN > ANNOUNCE); латентность-осознанный порядок кольца (mini-TSP по
  RTT); опц. спекулятивный хвост.
- **Результат:** «Kubernetes для мобильных ИИ» — самоперестраивающийся кластер.

## 6. Риски и честные оговорки

- **llama.cpp RPC сырой:** нет безопасности, нет churn-устойчивости, сырые тензоры (полоса),
  ориентирован на стабильный LAN. Это фича, а не баг — эти пробелы закрывает HELIX сверху.
- **LiteRT не шардится по слоям — не пытаться.** Использовать для 1 узла / малых моделей.
- **USB phone-to-phone** имеет практический нюанс «кто host» (OTG) — связка **телефон↔SBC**
  проще и мощнее; начинать с неё.
- **Префилл-полоса — реальный боттлнек**, планировать компрессию/чанкинг активаций с Phase 3.
- **RAM на устройстве** — не только веса: KV + буферы + оверхед; бюджетировать ≲2.5–3 ГБ/узел.
- **Android background limits:** держать меш в foreground-сервисе (уже заложено в
  `INTEGRATION.md` — `MeshService`), иначе OS убьёт узел.

## 7. Зафиксированные решения (2026-07-16)

- **Ближний срок — Track A: LiteRT + chat UI + routing-mesh.** Меш = пропускная способность
  (параллельные запросы) + failover, НЕ ускорение одного ответа, НЕ модель больше устройства.
- **Параллельно — Track B: GGUF/llama.cpp true-shard** держим открытым для «16B на 5»
  (модель больше устройства). ONNX — запасной.
- **USB-OTG — отложено** до Phase 4 (после Track B). Приоритетная цель тогда — телефон↔Linux-SBC.
- **Первым делом (A0/B0):** фиксы блокеров из `AUDIT2`.
