# Pointer Protocol — координация LiteRT-агентов на субстрате HELIX

Рабочий проект протокола «поинтинга»: распределённая координация нескольких **целых**
LiteRT-агентов на разных устройствах (обмен *смыслами/результатами*, не тензорами). Это
**Track A** (routing-mesh) — отдельно от тензор-шардинга HELIX (Track B). Документ
опирается на присланный набросок (Google Edge / MCP / A2A) и на уже построенный и
протестированный стек HELIX.

> Куда встраивается: HELIX + Pointer уходят в форк chatter-UI **отдельной веткой**; здесь —
> проектная спецификация и план, а не app-интеграция.

---

## 0. Что такое поинтинг здесь (и чем он НЕ является)

- **Не шардинг.** LiteRT физически не режет модель по слоям. Каждый узел держит **целую**
  (оптимизированную под мобильные) модель = один **агент**. «Поинтинг» = координатор
  «наводит» (points) задачи/подзадачи на агентов, собирает и агрегирует смыслы.
- **Это multi-agent orchestration**, а не новый транспорт. Значение даёт слой координации
  (кто что делает, как сливать ответы), а не «ещё один сокет».
- **Связь с HELIX:** тот же меш, та же безопасность. Меняется только верхний слой сообщений.

## 1. Проверка фактов из наброска (важно для дизайна)

| Утверждение | Статус | Следствие для дизайна |
|---|---|---|
| AI Edge Gallery поддерживает MCP | ✅ **подтверждено** (Android, экспериментально, поверх Streamable HTTP) | MCP = **вызов инструментов внутри агента** (RAG/web-fetch/Coder), не координация. Использовать как есть. |
| A2A — базовый протокол координации в экосистеме | ⚠️ **частично**: A2A реален (Google→Linux Foundation), но транспорт = **HTTP(S)+JSON-RPC+SSE**, Agent Card на well-known URL | На локальном меше **нельзя гонять A2A-по-HTTP**. Брать **схему** (Agent Card, Task-lifecycle), возить её по кадрам HELIX. A2A — для шлюза во «внешний мир». |
| MCP для агент-агентной координации | ❌ (набросок сам это отвергает — верно) | MCP остаётся intra-agent tool-layer. |

Вывод: набросок как продуктовый роадмап **разумен**, но (а) переизобретает транспорт/
безопасность/обнаружение, которые уже готовы в HELIX; (б) переоценивает пригодность A2A как
транспорта; (в) **не содержит модели угроз** — а у агентной координации есть свои
специфические атаки (см. §6).

---

## 2. Рычаг: не строить с нуля — переиспользовать субстрат HELIX

Присланный роадмап предлагает заново сделать AgentRegistry, Router, транспорт, обнаружение.
Всё это **уже есть и протестировано** в HELIX L1–L3. Pointer = новый слой сообщений поверх.

| Компонент из наброска | Уже готово в HELIX | Что до-строить |
|---|---|---|
| Транспорт (Wi-Fi/USB) | `helix/transport/` (IP-меш: Wi-Fi Aware/Direct/LAN/USB-tether) | — |
| Обнаружение (DISCOVER/ANNOUNCE) | `roster.py` + маяки/`ANNOUNCE` | нести **capabilities** (Agent Card), не только память |
| Безопасность | `frame.py`/`sealer.py` (AEAD, replay, версия, **identity-в-кадре**) | — (для Sybil — per-node identity, §6) |
| AgentRegistry | `Roster` (членство+живучесть) | расширить полем capabilities |
| Router / координатор | `control.py`/`orchestrator.py` | новые режимы (pipeline/parallel/voting) |
| Aggregator | сбор в `Session` | правила слияния/голосования |
| Живучесть/самолечение | `on_node_lost` + re-place | **проще**, чем в тензорах: подзадача переназначается др. агенту (идемпотентный re-run, нет KV) |
| Версия/разведение типов | `message.py` (`v` + типы) | Pointer — **под-протокол** (`subproto`), сосуществует с тензорным на том же меше |

Практически: агентная координация переживает уход узла **легче**, чем шардинг — нет KV и
чекпойнтов, потерянную подзадачу просто перезапускают на другом агенте.

## 3. Сообщения Pointer Protocol (агентный слой поверх кадра HELIX)

Все — обычные HELIX-сообщения: **зашифрованы, аутентифицированы, защищены от повтора,
`src` достоверен**. Под-протокол помечается, чтобы не путать с тензорными типами.

| Тип | Направление | Тело |
|---|---|---|
| `AGENT_ANNOUNCE` | агент → всем | Agent Card: модели, RAM, скорость, навыки/skills, типы задач, батарея |
| `STATUS` | агент → координатору | busy/free, текущая нагрузка/очередь |
| `TASK` | координатор → агенту(-ам) | task_id, mode (pipeline/parallel/voting), inputs, deadline, ссылка на контекст |
| `PARTIAL` | агент → координатору | task_id, потоковый фрагмент (стриминг) |
| `RESULT` | агент → координатору | task_id, финальный ответ + метаданные (score/uncertainty) |
| `VOTE` | агент → координатору | task_id, кандидат/оценка (режим voting) |
| `DECIDE` | координатор → всем | task_id, финальное решение/агрегация |
| `CONTEXT_SYNC` | любой → группе | **дельта** общего контекста (append-only, с провенансом `src`) |

`AGENT_ANNOUNCE` = локальный аналог A2A Agent Card, только по кадрам HELIX, не по HTTP.

## 4. Режимы координации (оркестрация поверх сообщений)

Координатор (`Orchestrator`-аналог) реализует три паттерна как драйверы над набором
сообщений — так же, как L5 драйвит тензорное кольцо:

- **Pipeline** (поиск → анализ → генерация): `TASK`→`RESULT`→ следующий `TASK` с
  результатом предыдущего в контексте. Уход узла → переназначить *этот шаг* другому агенту.
- **Parallel** (N агентов над одной задачей): `TASK` веером → сбор `RESULT` → Aggregator
  сливает (конкатенация/резюмирование/лучший-по-score). Кворум K-из-N для устойчивости к
  плохим ответам.
- **Voting**: `TASK` веером → сбор `VOTE` → `DECIDE` по правилу (большинство / лучший score
  / судья-агент). **Требует защиты от Sybil** (§6).

Терминация и стриминг — как в L5: явный статус `COMPLETED/TIMEOUT/FAILED`, поток `PARTIAL`.

---

## 5. Синхронизация контекста = дельта (узкое место)

Аналог префилла из тензор-мира: **контекст — главный пожиратель полосы** в мультиагенте.

- Хранить общий диалог как **append-only лог операций**; `CONTEXT_SYNC` несёт **дельту**, не
  весь контекст (набросок верно ловит это в Фазе 7 — но это должно быть в ядре, не в конце).
- **Контент-адресуемые префиксы**: одинаковый системный промпт/документ шлётся хешем, а не
  телом (дедуп по меш).
- Каждая дельта помечена аутентифицированным `src` (провенанс) — критично для §6.

---

## 6. Модель угроз (чего в наброске нет вообще)

Транспортный уровень уже закрыт HELIX (шифрование, подпись, replay, identity-в-кадре). Но у
**агентной координации свои угрозы**, которых нет у голого шардинга:

1. **Sybil-голосование.** Одно устройство поднимает много «агентов», чтобы выиграть
   `VOTE`/кворум. Митигция: **один узел — один голос**, вес по аутентифицированной
   идентичности узла. Claim-tracking HELIX (один пир → один node_id) помогает частично;
   полная защита — **per-node асимметричная идентичность (HELIX ④)** + опц. аттестация (③).
2. **Отравление результатов.** Вредоносный/сломанный агент возвращает мусор/адверсариальный
   ответ. Крипта тут не спасает — это про доверие/качество. Митигция: кворум-согласие
   (parallel), судья-верификатор, репутация. Обязательно заложить в правила `DECIDE`.
3. **Prompt-injection через `CONTEXT_SYNC`.** Общий контекст — вектор атаки: агент внедряет
   инструкции в общий диалог, перехватывая поведение других агентов (см. исследования по
   «protocol exploits» в LLM-воркфлоу). Митигция: трактовать межагентный контекст как
   **недоверенный ввод**, провенанс-тегирование дельт по `src`, не превращать вывод одного
   агента в системную инструкцию другого без ограждения.
4. **DoS задачами.** Агент спамит `TASK`/`CONTEXT_SYNC`. Митигция: `STATUS`-backpressure,
   лимиты/приоритеты задач (Фаза 7 наброска).

---

## 7. Где живут MCP и A2A

- **MCP — внутри агента.** Каждый агент использует MCP для вызова инструментов (RAG,
  web-fetch, Coder) — это уже поддержано Gallery. Pointer Protocol **не заменяет** MCP.
- **A2A — на границе.** Для интеропа с внешними (облачными) агентами поднять **A2A-шлюз**:
  узел-gateway говорит наружу A2A-по-HTTP (Agent Card, Task-lifecycle), внутрь — Pointer по
  HELIX. Так локальный меш остаётся эффективным, а внешние агенты видят стандартный A2A.

## 8. Фазовый план (переработанный, с переиспользованием HELIX)

- **P0 — субстрат.** Взять HELIX L1–L3 (готово+протестировано). Определить Pointer как
  под-протокол (`subproto` + типы §3). *Нового кода почти нет.*
- **P1 — реестр агентов.** Расширить `Roster` полем capabilities (Agent Card); `STATUS`.
- **P2 — одиночная задача.** `TASK`→`PARTIAL`→`RESULT`; минимальные Router+Aggregator
  (переиспользовать паттерн `Session`/стриминг из L5).
- **P3 — parallel + voting.** Сбор N результатов/голосов; правила `DECIDE` (кворум,
  best-score, судья).
- **P4 — pipeline + контекст.** Последовательные шаги; `CONTEXT_SYNC` дельтой (§5).
- **P5 — MCP-инструменты.** Подключить инструменты внутри агента (Gallery MCP уже есть).
- **P6 — безопасность.** Per-node identity против Sybil (HELIX ④), провенанс/анти-инъекция
  для контекста (§6).
- **P7 — интероп/масштаб.** A2A-шлюз наружу; кэш контекстов, дельта-передача, приоритеты.

Сценарии тестирования из наброска (одиночный / parallel+voting / pipeline на 3–5 устройствах,
замер задержки/памяти/надёжности) — оставить как есть, они адекватны.

## 9. Что проверить / точки интеграции

- **Интеграция с chatter-UI форком** (отдельная ветка): где Router инстанцируется (сервис/
  ViewModel), как `PARTIAL`-стрим попадает в UI, тумблер «Pointer mesh».
- **Gallery MCP** — экспериментальный и через HTTP-MCP-сервер; продумать, какие инструменты
  агент реально дергает офлайн.
- **A2A-версия** схемы Agent Card (двигается быстро) — зафиксировать при постройке шлюза.

## 10. Итог

«Поинтинг» — это **Track A на субстрате HELIX**: транспорт, шифрование, обнаружение,
членство, живучесть и самолечение переиспользуются; строится только **агентный слой
сообщений + режимы координации + модель угроз**. Присланный роадмап хорош как продуктовая
рамка, но его нужно (1) посадить на готовый субстрат вместо переизобретения, (2) поправить по
A2A (концепции, не HTTP-транспорт), (3) дополнить моделью угроз (Sybil-голоса, отравление
результатов, инъекция через контекст) — иначе повторится тот же провал приоритетов, что и в
прошлых внешних обзорах: продукт, у которого «работает», но который небезопасен.
