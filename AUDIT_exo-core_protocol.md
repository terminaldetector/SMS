# Технический аудит протокола `exo-core` для локальных ИИ-меш-систем

**Объект аудита:** `exo-core` — дистиллированное ядро оркестрации распределённого
инференса (порт из `exo-explore/exo`), предназначенное для запуска на Android через
Chaquopy поверх BLE-меша `bitchat-core`. Аудит охватывает **протокол взаимодействия
узлов** (`exo_core/networking/*`, `exo_core/node.py`, `exo_core/inference/sharded.py`)
и связанную логику размещения/шардинга.

**Метод:** чтение всего исходного кода ядра, запуск штатного self-test
(`python -m exo_core.selftest` → `ALL PASSED`) и написание точечных репро,
воспроизводящих проблемы в условиях, приближенных к реальному транспорту (потеря
петлевой доставки, переупорядочивание, подмена кадров).

**Общий вывод:** оркестрационная логика (разбиение по памяти, назначение шардов,
кольцевой конвейер) корректна и хорошо покрыта тестами *в идеальном транспорте*. Однако
**сам протокол спроектирован под надёжный, упорядоченный, доверенный канал с
петлевой доставкой самому себе** — а целевой транспорт (BLE-меш) не даёт ни одного из
этих свойств. Три из этих несоответствий приводят к полному отказу генерации на
реальном меше и **не видны в self-test**, потому что `InMemoryMeshNetwork` случайно
обеспечивает все недостающие гарантии.

## Критические находки

### 1. 🔴 Протокол требует петлевой доставки самому себе (`send_to(self)`)

**Где:** `exo_core/node.py` — `generate()`/`_handle_assign`/`_handle_prompt`;
`exo_core/networking/mesh.py` — `InMemoryMeshNetwork.send_to`.

**Суть.** В `plan()` координатор всегда включает себя в кольцо (`ring_ids =
[self.node_id] + sorted(others)`) и получает собственную полосу слоёв. Далее
`generate()` рассылает `ASSIGN` **каждому** узлу кольца, включая себя, и отправляет
первый `PROMPT` на `ring[0]` — который тоже может быть самим координатором:

```python
for nid in cycle.node_ids:            # включает self
    self._outbox.append((str(nid), proto.assign(...).encode()))
...
self._outbox.append((ring[0], proto.prompt(...).encode()))
```

То есть, чтобы координатор выполнил свою часть конвейера, транспорт обязан **доставить
сообщение, отправленное самому себе, обратно в его же `_on_message`**.
`InMemoryMeshNetwork.send_to` это делает (ищет узел в общей шине и вызывает его
обработчик, даже если это отправитель). А реальный мост (`ExoMeshBridge.sendTo` →
`bitchat core.sendPrivate(msg, nodeId)`) отправлять приватное BLE-сообщение самому себе
**не будет** — это no-op.

**Воздействие.** На любом реальном многоустройственном запуске шард координатора
(полоса `[0, k)`, включающая embedding) **не загружается и не исполняется**. Результат —
пустой или некорректный вывод. Ошибка полностью маскируется self-test'ом, потому что
in-memory шина случайно обеспечивает петлю.

**Доказательство (репро).** Подкласс меша, где `send_to(self)` — no-op (как на BLE):

```python
class NoLoopbackMesh(InMemoryMeshNetwork):
    async def send_to(self, node_id, message):
        if node_id == self.node_id: return   # bitchat sendPrivate(self) — no-op
        await super().send_to(node_id, message)
```

Тот же сценарий, что в self-test (`nodeA` 8 ГБ + `nodeB` 4 ГБ, `demo-llm`), даёт:

```
nodeB assigned layers [4,6) rank 1/2        # nodeA НЕ назначен
RESULT: ''                                   # ожидалось 'hello world foo bar'
```

**Рекомендация.** Не гонять кадры через транспорт для самого себя. Координатор должен
обрабатывать собственные `ASSIGN`/`PROMPT` локально (прямой вызов `_handle_*` или
внутренняя очередь), а `_flush`/адаптер — короткозамыкать `target == self.node_id` в
локальную доставку. Добавить в self-test вариант меша **без** петли, чтобы регрессия
ловилась.

### 2. 🔴 Отсутствие аутентификации и целостности на уровне протокола

**Где:** `exo_core/node.py::_on_message` и весь `exo_core/networking/protocol.py`.

**Суть.** Кадры — это открытый JSON без подписи, без счётчика, без привязки к
отправителю. Обработчик получает `from_node` от транспорта, но **полностью его
игнорирует** и доверяет полям тела:

- `ANNOUNCE`: `self._peers_memory[msg.body["node_id"]] = Memory(int(msg.body["memory"]))`
  — узел объявляет **любой** `node_id` и **любой** объём памяти.
- `ASSIGN`: принимается от кого угодно и переопределяет `self._ring` и полосу слоёв —
  любой пир может переназначить топологию всего кольца.
- `PROMPT`: несёт `coordinator` в теле; последний стейдж шлёт токены туда, куда указано —
  можно указать жертву (перенаправление трафика) или выдать себя за координатора.

Проект опирается на шифрование Noise в `bitchat-core`, но Noise защищает **канал/BLE-peer**,
тогда как `node_id` — это **прикладной** идентификатор, никак не связанный с
криптографической идентичностью BLE-пира. Соответствия «`from_node` == заявленный
`node_id`» протокол не проверяет.

**Воздействие.** Один вредоносный (или сбойный) узел меша может: захватить размещение,
подделать назначения шардов, спуфнуть координатора, устроить отказ в обслуживании.

**Доказательство (репро).** Устройство с 1 ГБ объявляет 1 ТБ:

```
forged = proto.announce("liar", Memory.from_gb(1024).in_bytes).encode()
# coord.plan(...) →
  coord: layers [0,1)  (1 of 6)
  liar:  layers [1,6)  (5 of 6)      # «лжецу» досталось 5 из 6 слоёв
```

«Лжец» стоит на кольце и пропускает через себя весь трафик конвейера — при реальной
нехватке памяти он либо падает по OOM, либо вешает генерацию.

**Рекомендация.** Минимум: сверять `from_node` с заявленным `node_id` и принимать
`ASSIGN` только от узла, которого этот узел признал координатором для данной задачи.
Правильно: подписывать кадры ключом устройства и привязывать `node_id` к
криптоидентичности BLE-пира из `bitchat-core`. Добавить sanity-границы на объявляемую
память.

## Высокие находки

### 3. 🟠 Нет секвенирования и подтверждений — переупорядочивание/потеря рвут генерацию

**Где:** `node.py` (сбор `TOKEN`/`DONE`), `inference/sharded.py` (`ACTIVATION`/`FEED`).

Протокол предполагает надёжную, ровно-однократную доставку **по порядку**. Поле `step`
в `ACTIVATION`/`FEED` присутствует, но нигде не используется для контроля порядка,
дедупликации или ретрансмиссии — оно только эхом переносится. Последствия на лоссовом
многохоповом BLE-меше:

- Потеря одного `ACTIVATION` → кольцо вешается навсегда (до таймаута), без ретрая.
- Дубликат `FEED` → двойное продвижение шага.
- `DONE` обгоняет `TOKEN` → координатор выходит из цикла сбора и возвращает усечённый
  вывод.

**Доказательство (репро).** Меш, задерживающий доставку `TOKEN` на один тик (то есть
`DONE` приходит раньше), на штатном сценарии self-test даёт `RESULT: ''` вместо полного
ответа.

**Рекомендация.** Ввести per-task счётчики последовательности и переупорядочивающий
буфер на приёмнике; подтверждать/ретрать `ACTIVATION`; закрывать задачу по `DONE`
только после получения всех токенов вплоть до финального `step`.

### 4. 🟠 Гонки данных между потоком транспорта и asyncio-петлёй

**Где:** `node.py` (`_outbox`, `_collected`, `_done_tasks`), `sharded.py` (`_outbox`,
`_tokens`, `_done`).

`_on_message` вызывается синхронно из потока транспорта (для моста Chaquopy — из
Kotlin-потока), а `_flush()`/`generate()` работают в потоке asyncio-петли. Обычный
`list` меняется из обоих: `self._outbox.append(...)` из колбэка и `self._outbox.pop(0)`
из петли — не атомарно; аналогично `dict.setdefault(...).append(...)`. В self-test всё
однопоточно, поэтому проблема не проявляется, но на реальном мосте это гонки/порча
состояния.

**Рекомендация.** Складывать входящие кадры в потокобезопасную очередь (или маршалить в
петлю через `loop.call_soon_threadsafe`), а всё изменяемое состояние узла держать в петле.

### 5. 🟠 Тихое усечение по таймауту

**Где:** `node.py::generate` (`while ... and loop.time() < deadline`),
`sharded.py::generate`.

По истечении `timeout_s` метод просто возвращает то, что накопилось
(`"".join(self._collected.get(task_id, []))`). Отличить успешное завершение от
потери `DONE`/таймаута/усечения невозможно — вызывающая сторона получает «правдоподобный»
неполный ответ без признака ошибки.

**Рекомендация.** Возвращать статус завершения (done/timeout) либо бросать при таймауте;
логировать частичный сбор как ошибку.

## Средние находки

### 6. 🟡 Зависимость от порядка `ASSIGN` → `PROMPT` без буферизации
`_handle_prompt` начинается с `assert self._shard is not None, "received PROMPT before
ASSIGN"`. `ASSIGN` (via `send_to`) и `PROMPT` (via `send_to ring[0]`) кладутся в outbox
координатора и флашатся по порядку, но порядок доставки на BLE **не гарантирован**.
`PROMPT`, пришедший раньше `ASSIGN`, вызывает `AssertionError` (в проде — тихий сброс в
`BitChatNetworkAdapter.onMessage`), и генерация зависает до таймаута. Нужна буферизация
ранних `PROMPT` до применения `ASSIGN`.

### 7. 🟡 Перегрузка типов сообщений и отсутствие версии протокола
Тип `TOKEN` означает разное в двух под-протоколах: в `node.py` тело `{task_id, text}`,
в `sharded.py` — `{task_id, token_id}`; `DONE` общий. Если на одном меше сосуществуют
`ExoNode` и `ShardedPipeline` (или кадры перепутаны), декодер читает не тот ключ →
`KeyError`. Поля версии протокола/идентификатора под-протокола нет — нет ни
разграничения, ни forward/backward-совместимости. Рекомендуется добавить `version` и
`subproto` (или развести типы: `PROMPT_TOKEN` vs `SHARD_TOKEN`).

### 8. 🟡 Проверка памяти только по сумме кольца
`filter_cycles_by_memory` проверяет, что суммарная RAM кольца ≥ `storage_size`, но
`allocate_layers_proportionally` может выдать узлу полосу, превышающую **его личную**
RAM (гарантируется лишь ≥1 слой на узел). Апстрим-`exo` это дополнительно скорил; здесь
проверка снята. Возможен OOM на слабом узле кольца. Нужна проверка «полоса ≤ доступная
память узла» на этапе назначения.

### 9. 🟡 Нет лимитов на размер кадра/blob
`Message.decode` вызывает `json.loads` над произвольными байтами без ограничения размера;
`ACTIVATION` несёт base64-blob в JSON. Вредоносный пир может прислать гигантский кадр →
исчерпание памяти. Нужны лимиты размера на приёме и защита при разборе.

### 10. 🟡 Детерминированный `task_id` и утечка состояния координатора
`task_id = "task-" + model_card.model_id` (`node.py::generate`) не уникален: две
одновременные генерации одной модели используют один и тот же id → коллизия
собранных токенов. Плюс `_collected`/`_done_tasks` никогда не очищаются — рост памяти на
долгоживущем узле. Использовать `new_runner_id()` и вычищать состояние по завершении.

## Низкие находки / эффективность

- **11.** `node_id` не привязан к транспортному `peerID`; `from_node` в `_on_message` не
  используется даже для базовой сверки (см. также #2).
- **12.** Обнаружение узлов держится на гонке: `plan()` использует `_peers_memory`
  (наполняется только из `ANNOUNCE`), а не `mesh.get_nodes()`. Если `generate()`
  стартует раньше, чем разошлись `ANNOUNCE`, кольцо будет неполным. Нужен барьер/кворум
  либо использование `get_nodes()`. Сейчас `get_nodes()` в оркестрации не задействован.
- **13.** JSON+base64 для скрытых состояний даёт ~33 % overhead и перекодирование на
  каждом хопе — на BLE это дорого (авторы честно отмечают бинарный путь как future work).
- **14.** Координатор — единая точка отказа (rank 0, владеет embedding), переизбрания
  нет (election удалён при дистилляции). Для «меша» стоит хотя бы задокументировать
  восстановление при падении координатора.

## Что сделано хорошо

- Чистая абстракция транспорта `IMeshNetwork` (`broadcast`/`send_to`/`get_nodes`/
  `register_handler`) — протокол действительно транспортно-агностичен.
- Логика разбиения по памяти (`allocate_layers_proportionally`, largest-remainder)
  портирована практически дословно и корректна; хорошее покрытие граничных случаев
  (≥1 слой на узел).
- Отличный, самодостаточный self-test без сторонних зависимостей, включая доказательство
  того, что **обе** полосы реально исполняются (`NumericShardRunner`, шаг `[8]`).
- Честная документация ограничений (`DISTILLATION_REPORT.md`, `BACKENDS.md`,
  `SHARDING.md`): бинарный транспорт, экспорт под-моделей и т. п. явно помечены как
  оставшаяся работа.
- Разумная граница Python↔Kotlin (строковый контракт `poll()` → JSON), одинаково
  работающая под Chaquopy и на CPython.

## Приоритетный план исправлений

1. **Убрать зависимость от петлевой доставки (#1).** Локальная обработка собственных
   `ASSIGN`/`PROMPT` координатором + тест на меше без петли. *Блокер для реального
   железа.*
2. **Ввести per-task секвенирование, буфер переупорядочивания и ретрансмиссию `ACTIVATION`
   (#3, #6); закрывать задачу по `DONE` только после всех токенов; возвращать статус
   завершения (#5).** *Блокер корректности на лоссовом меше.*
3. **Потокобезопасность приёма (#4):** очередь + маршалинг в петлю.
4. **Модель доверия протокола (#2, #11):** сверка `from_node`/`node_id`, приём `ASSIGN`
   только от признанного координатора, подпись кадров, привязка к BLE-идентичности,
   sanity-границы на память; лимиты размера кадра/blob (#9).
5. **Гигиена (#7, #8, #10, #12):** поле версии/под-протокола, проверка «полоса ≤ RAM
   узла», уникальные `task_id` + очистка состояния, кворум-барьер обнаружения.
